# TuneVis

Music discovery, audio-feature analysis and ranking web app. Vanilla HTML/CSS/JS (ES modules, no bundler, no framework), hosted on Vercel.

## Architecture
- **Spotify auth**: Client Credentials flow. The browser calls the Vercel serverless proxy `/api/token` (holds the client secret) and caches the token in localStorage (`spotify_cc_token`, ~1hr lifetime). No Spotify user login (Spotify dev mode caps at 5 users, which is why this design was chosen).
- **TuneVis accounts (Supabase)**: own email + password accounts, modelled on the developer's racing map site. supabase-js is loaded with a dynamic `import()` from a pinned jsdelivr build in `scripts/supabase.js` (`getSupabase()` returns null if unconfigured or the CDN fails, so account code must never block the music pages). Public URL + anon key live in `scripts/supabase-config.js`; empty = accounts off (no header button, no Save buttons). Email links use token_hash templates landing on `auth-confirm.html` (setup steps in README). Schema in `supabase/schema.sql`, run by hand in the SQL editor; every table has RLS and `on delete cascade` from `auth.users`. The service-role key is only used server-side in `api/delete-account.js`, which takes the user from the verified token, never the body.
- **What accounts save**: rankings (`public.rankings`; the row stores the same state as the ranking URL, reopened via `rankingUrl()` with `?saved=<id>` so saving again updates that row) and recently viewed (`public.recently_viewed`, trimmed to 10 by trigger). Recently Viewed is signed-in only: `saveToRecent` records nothing while signed out, the home tab shows a log-in prompt (`#recent-signin`) instead, and the localStorage copy is just a cache of the account's list, cleared on sign in, sign out and account deletion (`clearRecentCache`). `home.html?tab=recent` opens that tab.
- **Usernames** (`public.profiles`, Nov 2026 migration at the end of `supabase/schema.sql`): one per account, 3–20 letters/numbers/underscores, unique ignoring case, reserved words blocked by a check constraint (mirrored in `profile.js`). Chosen and changed on the account page with a live availability check (`username_available()` RPC, security definer, true/false only). Only the owner can read their profile for now; showing usernames to others will need its own policy. A display copy lives in the account's `user_metadata.username` so the header chip can show it without a query; it's re-validated before display and never trusted for anything else.
- **Logo / brand**: wordmark in Fredoka 600 (Google Fonts, loaded on every page) with a pink→violet gradient (`#ff9ad8 → #d68bff → #a98bff`) over green bars (`url(#tv-bars)` gradient defined in each page's logo SVG). Body text still falls back to the system font: "Poppins" is named in the CSS but never loaded.
- **Icons**: the head tags copy the racing map site (racing-map.vercel.app), whose home-screen icon worked first time: just `<link rel="icon" href="/icons/icon-512.png?v=N" sizes="512x512" type="image/png">`, `<link rel="apple-touch-icon" href="data:image/png;base64,…" sizes="180x180" type="image/png">` (the 180px PNG embedded as a data URI, about 2.3 KB: iOS's Add to Home Screen sheet loads icons with its own loader and kept showing a letter tile with a normal URL; re-embed from `apple-touch-icon.png` on every page if the icon changes) and the manifest link, plus the status-bar-style and title metas. No SVG favicon or .ico link (iOS can't use an SVG for the home screen and fell back to a letter tile), no `apple-mobile-web-app-capable` metas, and the manifest has no `id`/`scope` and three icons (192, 512, maskable 512). The app icons are the 3 coloured bars on plain black, full-bleed, opaque RGB, 2–6 KB, drawn from `icons/app-icon.svg`; redraw from it rather than hand-edit the PNGs. Copies of the touch icon live at `/apple-touch-icon.png`, `/apple-touch-icon-precomposed.png`, `icons/apple-touch-icon.png` and the sized root names iOS probes (`/apple-touch-icon-{120,152,167,180}x…[-precomposed].png`). `favicon.ico` and `icons/favicon-*.png` / `favicon.svg` (3 bars on a dark rounded square) are kept as files but not linked. Bump `?v=N` on every page whenever the icons change. A home-screen shortcut keeps whatever icon it saw when it was added, so test by deleting and re-adding it. Every page has `og:` / `twitter:` tags pointing at `https://tunevis.vercel.app/icons/og-image.png` (the live site).
- **Album star ratings** (Nov 2026 ratings/folders migration): `rankings.rating`, 0.5–5 in half steps, album rankings only (check constraint). `star-rating.js` provides the widget (`createStarRating`, slider role, arrow keys, left/right half of a star = .5/whole, or press and drag along the stars and release: pointer capture, `touch-action: pan-y` so vertical swipes still scroll, `pointercancel` drops the drag) plus `starsHtml` / `starsText` for display. On `rank.html` it sits under the album name, travels in the URL as `rating`, is part of the saved record and `comparable()`, and appears in exports. An album can be saved with only a rating (no tracks ranked yet); the Save button requires ranked items or a rating. The value label and Clear button keep a fixed width so the stars never shift under the pointer.
- **Saved rankings page and folders**: `rankings.html` shows saved rankings as a grid of cards (large square cover, round for artists; name, a short line, stars; 2 columns on phones, `auto-fill minmax(150px)` otherwise; first 8 then "Show all N"). Tabs: Albums, Artists (with Top tracks / Albums & EPs sub-tabs, `#sub-tabs`, same order as the artist ranking page's toggle) and Custom (favourite artists / tracks, once one exists). Each tab or sub-tab is a section (`sectionOf(kind)` in `saved-rankings.js`: album, artist, artist_albums, favourites; mirrored by `public.ranking_section()` in SQL; `?type=<section>` in the URL, `?type=artists` opens the Artists tab, default the first with rankings). Each section has its own folders: `ranking_folders.section` (Nov 2026 folders-by-kind migration; names unique per user per section, ignoring case; the RLS policy on `ranking_folder_items` only lets a ranking into a folder of its own section; the migration split any existing mixed folder into one same-named folder per section). `ranking_folder_items` is many-to-many (a ranking can be in several folders; deleting either side cascades only the link). In each tab: folder chips (All + the tab's folders with counts, `?folder=<id>`), + New folder, and Rename / Delete folder under the list. The list rows only open the ranking: Add to folder and Delete ranking live on the ranking's own page (`rank-view.js`). A search box beside the "Your saved rankings" title (`#saved-search-input`, full width on phones) filters by name, artist/album, kind and folder names (case- and accent-insensitive, every word must match); tab and folder counts show matches, results aren't collapsed, and it's cleared on `pageshow`. Most recent / Highest stars switch (albums by their rating, artists by their average; rated first, highest first, ties and unrated by most recent), remembered per browser in localStorage (`tunevis_saved_sort`). Before the folders-by-kind migration `loadFolders()` reports `sectioned: false` and folders are shared by every tab, as before. Hover colours on these buttons are inside `@media (hover: hover)`: on phones a tap leaves hover stuck on whatever lands under the finger (Delete folder went red).
- **Social** (Nov 2026 social migration, last block of `supabase/schema.sql`, modelled on the racing map site's friends; verified on PGlite with three users): `friendships` (one row per pair, unique on least/greatest; `pending` → `accepted`; only the addressee can accept, either side deletes = decline / cancel / unfriend; both sides need a `profiles` row) and `ranking_posts` (a ranking shared to the feed with an optional caption ≤ 280; shows the ranking as it is now; cascades with the ranking). Security-definer helpers `is_friend()` / `knows()`; `search_profiles(p_query)` (username prefix, 2+ chars, LIKE wildcards escaped, max 10, never yourself, returns only user_id + username) and `profile_by_username()`. New policies: profiles readable by anyone you `knows()`; **rankings readable by friends** (writes stay owner-only); posts readable by author and friends, insertable only for your own rankings. Because friends' rankings are now readable, `listRankings()` filters `user_id = me` and `initSaveButton` only treats a saved id as yours if `user_id` matches; any new "my rankings" query must filter by user too. Folders and recently viewed stay private. A friend's ranking opens with `from=<id>` (`rankingUrl(r, { friend: true })`) instead of `saved=`: view only, Edit / Save / folder / delete hidden, "Ranked by @user" byline and "Rank it yourself" (`setFriendRanking()` in rank-view.js). Your own saved ranking's view has **Share to feed** (caption dialog; notes when it was last shared). Data helpers in `social-data.js` (fall back to `available: false` before the migration); UI pieces (avatars from the username's hue, `timeAgo`, friend buttons, `postHtml`) in `social-ui.js`; cards shared with the saved grid in `ranking-cards.js`.
- **Artist average stars** (`artist-ratings.js`): the mean of the user's album ratings for an artist's albums (each album once, newest rating), shown on Artists cards ("4.2 avg") and under the artist's name on `rank.html` ("average from N rated albums"). Album rankings don't store their artists, so `tunevis_album_artists` in localStorage maps album id → artist ids: filled when an album ranking page opens (`rememberAlbumArtists`) and, for rated albums not in it, by `/v1/albums?ids=` in batches of 20 (401 retry). No TTL (credits don't change), capped at 2000 entries; listed in the privacy policy.
- **Artist album rankings** (Nov 2026 migration): adds `artist_albums` to the rankings kind check. The original kind/source checks were unnamed, so the migration finds them via `pg_get_constraintdef` and replaces them with named ones (`rankings_kind_check`, `rankings_source_check`). `schema.sql` (all migrations) was verified on PGlite.
- **Before a migration is run**: `saved-rankings.js` falls back when the `rating` column or folder tables don't exist yet (Postgres 42703 / PostgREST PGRST204 / PGRST205): rankings still list and save without the rating, and the folder UI hides. Keep this pattern for future columns that the client depends on.
- **Landing page** (`index.html`): "Log in" button plus Forgotten password / Sign up / Continue without signing in links; no header account button there.
- **Stale tokens**: every fetch wrapper (`spotifyGet` / `spotifyFetch`) retries once on 401 via `getSpotifyToken(true)`. Keep this pattern for any new Spotify call.
- **Other APIs**: Last.fm (trending charts, genre tag charts, `track.getSimilar`), ReccoBeats (audio features, with multi-pass fallback search for older catalog).
- **State**: localStorage for caches (1hr TTL, keyed per mode+genre) and recently viewed; URL query params for shareable ranking state (`mode`, `genre`, `size`, `order`, `name`) via `history.replaceState`.

## Pages and scripts (scripts/ and styles/style.css, one shared stylesheet)
- `index.html` – landing page (Log in button, account links).
- `social.html` + `social.js` – Social section (third link in the Discover | Rankings | Social switcher on home, rankings and social pages; noindex, not in the sitemap). Gates: signed out → Log in / Sign up; no username → link to `account.html#username-form`; migration not run → "not switched on yet". Tabs (`?tab=feed|friends|find`): Feed (your and friends' posts, newest 40, remove your own), Friends (requests with Accept / Decline and a pink count badge, friends with Remove, requests you've sent with Cancel; opens here when a request is waiting), Add friends (debounced username search, `@` stripped, requestId guard, cleared on pageshow).
- `profile.html` + `profile-page.js` – `?u=<username>` (any case): avatar, friend button, and for friends (or yourself) their saved rankings as cover cards in Albums / Artists / Custom tabs, opening read-only; others are told rankings are shared between friends. noindex.
- `about.html`, `faq.html`, `privacy.html`, `terms.html`, `404.html` + `content-page.js` – content pages (article layout, `.content-article`). Vercel serves `404.html` for any missing URL, so it uses root-relative links (`/styles/…`, `/home.html`). The privacy policy describes exactly what is stored (accounts, rankings, ratings, folders, recently viewed, local storage keys) and which providers are used: update it whenever that changes.
- `home.html` + `home.js` – song search (debounced live), Trending tab (genre dropdown, 12 curated genres) and Recently Viewed carousel, Rankings nav button. (The old About pop-up is now `about.html`.) The home, rankings and social pages share the same large logo header with a Discover | Rankings | Social section switcher inside it (`.section-nav`, `aria-current="page"` on the active one; no back button on either), so switching sections doesn't change the logo. In that header whose bars are pinned to the title (`top: 72px` / `87px` on phones) to stay clear of it.
- `features.html` + `features.js`, `features-data.js`, `features-charts.js` – audio-features dashboard for a track: charts, recommendations with score badges, clickable artist names opening a top-tracks modal, "coming soon" message when ReccoBeats has no features yet. Back button uses `history.back()`.
- `rankings.html` + `rankings.js` – search for an artist/album to rank, with a one-line "Make a custom ranking ›" link to `rank-general.html` straight under the search box (`.custom-rank-link`; it used to be a large box), then search results, then Recommended for you, then Your saved rankings.
- `recommended-rankings.js` – "Recommended for you" on `rankings.html` (signed in, with at least one album/artist ranking): the same cover cards as the saved grid, each with a green reason line, linking to a fresh `rank.html` ranking. Suggestion kinds, picked round-robin in this priority so the list mixes them (`pickVaried`, max 8, all in one looping horizontal row): albums in an artist's Albums & EPs ranking with no album ranking; artists of ranked albums with no artist ranking (opens their Albums & EPs list); the newest unranked album of artists whose top tracks are ranked; artists similar to the user's favourites (highest average stars first; Last.fm `artist.getSimilar`, resolved by exact-name Spotify search, one per seed); the top album of those similar artists (Last.fm `artist.getTopAlbums` + Spotify album search). Never suggests anything already ranked. Cached in localStorage (`tunevis_recs_cache`, 1 hour, keyed by user id + every ranking's id and updated_at) and recomputed on Back. Its classes are `suggest-*`: `.rec-card` is already the song page's recommendations carousel.
- `rank.html` + `rank.js` – artist/album ranking workspace: top 5/10 (artist) or top 5/whole album (album), tap-to-add desktop two-column layout, tabbed mobile layout, catalog search with per-result `+`, album-name search expands to tracks, Spotify embed play button. Artist pages have a Top tracks / Albums toggle (`list=albums` in the URL, saved as kind `artist_albums`); each list keeps its own state (`listState`). "Albums & EPs" come from `/artists/{id}/albums?include_groups=album,single`: Spotify has no EP type, so a "single" with 4+ tracks counts as an EP (Spotify's own app labels these EPs too); remix/karaoke/instrumental/sped-up bundles are dropped (`NOT_A_RECORD`). Editions are grouped by `albumKey()`, which only strips edition words (deluxe, edition, remaster(ed), expanded, anniversary, bonus, international); "live" and "version" are deliberately not edition words, so live albums and re-recordings like "(Taylor's Version)" stay separate. `pickEdition()` prefers the standard edition, else the earliest (The Snuts only have "W.L. (Deluxe)", so that's shown). Filtered locally by the search box. On an album ranking the header's artist names (`meta.artists`) link to that artist's ranking page: their newest saved artist ranking (albums or top tracks) if any, else a fresh `rank.html?type=artist&id=…` (`artistHref()`, using the saved list from `loadSavedAlbumRankings()`).
- `rank-view.js` – read-only "finished list" view shared by both ranking pages. A saved ranking (`saved=<id>` in the URL) opens in it; Edit switches to the workspace (`#rank-edit`, `edit=1` in the URL), and Done saves any changes (`saveCtl.isDirty()` / `saveCtl.save()`) and returns to the view. New, unsaved rankings always open in the workspace. A saved ranking's view has Add to folder (`openFoldersDialog` in `folder-dialog.js`, which offers only that section's folders and can create one) and Delete ranking (returns to `rankings.html?type=<section>`); pages report the saved ranking with `setSavedRanking()`, and the buttons show only when signed in. There is no Copy link button any more. In an artist's Albums & EPs ranking the view links each album to its own album ranking (`albumLink()`): the newest saved album ranking if there is one, shown with its stars or "N ranked", else a fresh `rank.html?type=album&id=…` with "Start ranking ›". Saved album rankings are loaded once per visit and reloaded when coming Back to the page.
- `rank-general.html` + `rank-general.js` – favourite artists / favourite tracks (global, not scoped), genre-filtered popular pool, independent ranking state per mode (`modeState`).
- `rank-share.js` – shared export helpers: `buildRankingText`, `buildRankingImage` (canvas PNG), `downloadCanvas`, `copyText`. Used by both ranking pages along with an editable list name (`#list-name-input`) and Export button/modal.
- `auth.js` – token helper, `esc()`, and recently viewed (`saveToRecent` / `getRecent` / `syncRecent`, which also sync to the account when signed in).
- `login.html`, `signup.html`, `forgot-password.html`, `update-password.html`, `auth-confirm.html`, `account.html` + `auth-pages.js` – account pages; each sets `<body data-auth-page="…">`. Post-login redirects go through `safeNext()` (same-site paths only).
- `account-nav.js` – round account button injected into the page header (moves the header's right-hand button left via `.has-account-chip`), showing the username's initial. Included on every music page.
- `rankings-library.js` – "Your saved rankings" on `rankings.html`: tabs by section, folders, ratings, sort; reloads on Back (`pageshow` persisted) since a ranking may have been deleted or filed meanwhile. `rankings.js` is only the artist/album search.
- `folder-dialog.js` – shared pop-ups: `openModal`, `openNameModal` (new / rename folder), `openFoldersDialog` (a saved ranking's folders).
- `star-rating.js` – half-star rating widget and display helpers.
- `spotify-open.js` – "Open in Spotify" buttons (`openInSpotifyHtml(type, id)`) on home track cards, the song page (under the player and on each recommendation) and the ranking header. Full songs play in the Spotify app, which avoids the embed's preview-only limit in home-screen web apps without any Spotify login or API restriction (the Web Playback SDK would need per-user Premium OAuth, i.e. the dev-mode user cap). Normal tabs use a plain `open.spotify.com` link; in home-screen mode on touch devices it tries the `spotify:` app URI first and falls back to the web player after 1.5 s if the page is still visible.
- `profile.js` – usernames: `usernameProblem`, `getMyUsername`, `isUsernameAvailable`, `saveUsername`, `syncUsernameToSession`.
- `saved-rankings.js` – `initSaveButton` (Save / Save changes / Saved ✓ on both ranking pages), `listRankings`, `deleteRanking`, `rankingUrl`. The saved list is shown on `rankings.html` (`#saved-rankings`).

## Conventions and gotchas
- **Every horizontal carousel loops** (Netflix-style) through `loopCarousel(row, { items, build, leftBtn, rightBtn })` in `loop-carousel.js`: Discover's search / Trending / Recently Viewed, the song page's recommendations and Recommended for you. The row gets a screen's worth of copies on each side (built with the same `build()`, so they work; `data-loop-copy`, aria-hidden); when scrolling settles inside the copies (140 ms after the last scroll event, never while a finger is down) it jumps by exactly one set's width with snapping and smooth scrolling switched off for that moment. Arrows wrap; rows that fit don't loop and hide their arrows. A ResizeObserver lays the row out again on width changes (including a hidden tab being opened) and keeps the place. Buttons are wired on the first call that passes them (a row can first be filled empty while loading). If page code puts something else in the row ("No results"), the helper leaves it alone. New carousels must use it, and must build cards from a function rather than appending them by hand. Spotify embeds in carousel cards use `loading="lazy"`. (Testing note: in a hidden browser pane smooth scrolling and scroll events don't run, so check the loop with instant scrolls.)
- Debounced searches use a `requestId` counter to ignore out-of-order responses; keep doing this.
- Persistent DOM nodes that get re-rendered must guard listeners with `dataset.*Wired` flags to avoid accumulation.
- Use HTML entity glyphs (`&#8592;`, `&#10005;` etc.) or small inline SVGs for icons. No icon font is loaded. Avoid characters that iPhones draw as colour emoji (e.g. ▶ `&#9654;`, ◀, ✔, ❤): use an inline SVG instead (see `PLAY_LABEL` in rank.js).
- Search inputs have `autocomplete="off"` and are cleared on every `pageshow` (not just `event.persisted`): browsers either restore a frozen page or refill typed text on Back, and both left old searches in the box.
- On phones the ranking workspace's track / suggestion names wrap to two lines (`-webkit-line-clamp: 2`, `overflow-wrap: anywhere`) instead of one truncated line.
- Pages that need footer pinning use `class="page-flex"` on body.
- The export canvas sets only an inline width (never height): CSS `max-width: 100%; height: auto` then scales it in proportion on phones.
- On phones the bottom of `.bg-layer` fades into `#121212`, the colour Safari paints under its toolbar and home indicator, so there is no hard black strip; keep that fade if the background changes.
- Canvas export loads images with `crossOrigin="anonymous"` and falls back to a placeholder on failure to avoid tainting.
- Any API- or URL-derived text interpolated into an `innerHTML` template must go through `esc()` from `auth.js` (names, subtitles, image URLs, ids in iframe `src`). `features.html?track=` takes raw JSON from the URL, so skipping this is an XSS hole. d3 `.text()` is already safe.
- **Mobile is supported on every page** (phones from 320px up). All mobile rules live in the "Responsive: tablets and phones" section at the end of `style.css` (768px, 480px, 360px), grouped by page; add new ones there. Check new UI at 320, 375 and 768px wide as well as desktop. Rules of thumb: grid columns use `minmax(0, 1fr)` (on the ranking pages a plain `1fr` let one long track title widen the phone page to ~700px) (a plain `1fr` grows to fit wide content like the recommendations carousel); inputs are 16px on mobile (smaller makes iOS zoom); D3 charts size from their container's `clientWidth`, not `window.innerWidth`, and `features-charts.js` redraws them when the window width changes; JS that sets inline `display` needs `!important` in CSS to hide it on mobile.
- `body.page-flex > * { flex-shrink: 0 }`: without it, pages taller than the screen squeezed their sections (body is `height: 100%`) and the big logo header slid up under the top edge on phones.
- **Song page charts**: in the desktop three-column layout `alignChartHeights()` (features-charts.js) draws the bar and scatter charts down to the bottom of the radar's content (radar stays square) so the three cards line up; it reruns after drawing and on width changes, and does nothing when the cards stack.
- Don't give `html` a background: body's colour must paint the canvas underneath `.bg-layer` (z-index -1); a background on `html` made body paint over the layer and hid the coloured glow.
- `.bg-layer` is `position: fixed; overflow: hidden` so the decorative circles never widen the page, and `height: 100lvh` so it also fills the space behind mobile browser toolbars (otherwise a black strip at the bottom).
- **Full-screen on phones**: every page's viewport tag has `viewport-fit=cover` and `apple-mobile-web-app-status-bar-style` is `black-translucent`, so in the home-screen app the background runs under the status bar and home indicator. `body` is padded by `env(safe-area-inset-*)` (0 in normal tabs) to keep content clear of them; keep new full-screen or fixed elements inside the safe area too.
- **Footer and SEO**: every page has the same `<footer class="site-footer">` (About · Help & FAQ · Privacy · Terms, credits, Spotify disclaimer) with `aria-current="page"` on its own link; change it on every page together. Each page has its own `<title>`, meta description, `og:title` / `og:description` and a canonical URL on `https://tunevis.vercel.app`; account pages and 404 are `noindex`. `index.html` and `about.html` carry WebApplication JSON-LD. `sitemap.xml` lists the public pages and `robots.txt` points to it; add new public pages to both. Song and ranking pages set `document.title` to what's on screen.

## Known state
- `api/token.js` is the Client Credentials proxy; it reads `SPOTIFY_CLIENT_ID` / `SPOTIFY_CLIENT_SECRET` from Vercel env vars. Local testing needs `vercel dev` with those set.
- Spotify user login (personalised experience) existed previously but was removed after Spotify tightened developer registration requirements. Don't reintroduce user-auth flows without checking current Spotify policy.
- The Last.fm API key is hard-coded in `home.js`, `features.js` and `rank-general.js`; the 401-retry fetch wrapper is duplicated per script.
- Accounts are live on the developer's Supabase project. Supabase's built-in email only reaches project team members until custom SMTP is set up.
- `privacy.html` and `terms.html` still show "[contact email to be added]" (marked `<!-- TUNEVIS_CONTACT_EMAIL -->`). The developer chose to leave it for now; add their chosen contact address there when they provide one (UK GDPR expects a contact).
- Ideas not yet built: genre-aware recommendations on features page, accessibility pass.
